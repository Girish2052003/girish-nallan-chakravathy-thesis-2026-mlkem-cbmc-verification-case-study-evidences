## 2. What was being verified

### 2.1 Frozen production implementation

The examined function is a file-local C function in `mlkem/src/poly.c`. Its core arithmetic is:

```c
const int32_t magic = 20159;
const int32_t t = (magic * a + ((int32_t)1 << 25)) >> 26;
int16_t res = (int16_t)(a - t * MLKEM_Q);
```

For the frozen build, `MLKEM_Q = 3329`. Defining

\[
q=3329,\qquad M=20159,\qquad B=2^{25}=33554432,\qquad S=26,
\]

the implementation calculates

\[
t(a)=\operatorname{ashr}_{26}(M a+B)
\]

and returns

\[
R(a)=a-q\,t(a).
\]

The source documentation says that the function computes the centered representative congruent to the input modulo `q`. The checked-in function contract is weaker and directly enforces only the centered output range:

```c
ensures(return_value > -MLKEM_Q_HALF &&
        return_value <  MLKEM_Q_HALF)
```

For `q=3329`, this is exactly

\[
-1664\le R(a)\le1664.
\]

The source also explicitly records a portability assumption: right shift of a negative signed integer is implementation-defined by the C standard, and the implementation assumes a sign-preserving arithmetic right shift.

### 2.2 Independent mathematical reference

The principal independent oracle was deliberately written without the production multiplier, rounding offset, or shift:

```c
static int32_t centered_oracle(int16_t a)
{
    int32_t u = (int32_t)a % 3329;
    if (u < 0) u += 3329;
    if (u > 1664) u -= 3329;
    return u;
}
```

This oracle first computes a Euclidean residue in `[0,3328]` and then maps residues `1665..3328` into the centered interval by subtracting 3329. Its independence is important: comparing the production function with a second copy of the same magic-multiply formula would provide weak circular evidence.

### 2.3 Meaning of “full domain”

The input type is `int16_t`, so the complete domain contains exactly 65,536 values:

\[
-32768\le a\le32767.
\]

CBMC represented nondeterministic `int16_t` inputs symbolically and translated the assertions into bit-vector/SAT obligations. This was not random testing and did not sample a subset of inputs. For the declared finite source-level model, a successful run means CBMC found no counterexample for any value in that complete domain.

For relational and parameterized theorems, more than one symbolic variable was used. The reported pair counts describe the mathematical domain represented by those variables; they do not mean that a conventional loop concretely enumerated trillions of test cases.

## 8. T4 — Unique multiplier in the declared safe design space

### 8.1 Purpose and design space

T4 asks why the multiplier is `20159`. Offset `2^25`, shift `26`, modulus `3329`, and the full `int16_t` input domain are fixed.

A symbolic multiplier `M` is considered in the declared design domain:

\[
0\le M\le64513.
\]

This is the complete nonnegative interval for which

\[
M a+2^{25}
\]

is representable as signed `int32_t` for every `int16_t a`. `64514` is the first unsafe value; at `a=32767`, its numerator is `2147484670`, which exceeds `INT32_MAX`.

### 8.2 Candidate function

\[
t_M(a)=\operatorname{ashr}_{26}(Ma+2^{25}),
\]

\[
R_M(a)=a-3329t_M(a).
\]

### 8.3 Properties

#### T4.P14 — Complete numerator-safe multiplier domain

For every `M` in `0..64513` and every `int16_t a`, the numerator is signed-`int32_t` representable, and wide (`int64_t`) and narrowed (`int32_t`) arithmetic shifts agree.

#### T4.P15 — Sufficiency and production binding of 20159

\[
R_{20159}(a)=C(a)=R(a)
\]

for all `int16_t a`.

#### T4.P16 — Exclusion of every smaller safe multiplier

\[
0\le M<20159\Longrightarrow
R_M(-31626)\ne C(-31626).
\]

#### T4.P17 — Exclusion of every larger safe multiplier

\[
20159<M\le64513\Longrightarrow
R_M(-31625)\ne C(-31625).
\]

#### T4.P18 — Two-witness uniqueness

Within the safe design domain:

\[
\bigl(R_M(-31626)=C(-31626)\ \land\
R_M(-31625)=C(-31625)\bigr)
\iff M=20159.
\]

P15 supplies full-domain existence. P16 and P17 supply complete exclusion on either side. Together they prove uniqueness in the declared domain.

### 8.4 Results and C4 controls

P14–P18 passed. Ten controls covered zero, neighboring multipliers `20158/20159/20160`, the maximum safe value, the first unsafe value, and production binding at `INT16_MIN` and `INT16_MAX`.

### 8.5 T4 mutants

| Mutant | False change | Result |
|---|---|---|
| T4-M1 | Claim unique multiplier is 20158 | P18 failed; P14–P17 remained successful |
| T4-M2 | Replace lower discriminator `-31626` with `-31625` | P16 failed; P18 failed consequentially |
| T4-M3 | Replace upper discriminator `-31625` with `-31626` | P17 failed; P18 failed consequentially |

### 8.6 Exact scope of uniqueness

The result does **not** claim that 20159 is unique among:

- negative multipliers;
- different offsets;
- different shifts;
- wider or arbitrary intermediate types;
- different input domains;
- every possible Barrett-reduction construction.

It proves uniqueness in the explicitly defined nonnegative numerator-safe domain with the remaining parameters fixed.

### 8.7 T4 conclusion

Within that precise design space, `20159` is not merely a conventional choice: it is the only multiplier that yields exact centered reduction for every signed 16-bit input.

## 13. Assumptions, trusted base, and proof boundaries

### 13.1 No input assumptions versus modelling assumptions

The principal harnesses contain zero `__CPROVER_assume` statements. That means input domains were not silently reduced by assumptions. It does **not** mean the work is assumption-free in an absolute philosophical sense.

The result depends on the following explicit modelling and trusted-base assumptions:

1. **CBMC correctness:** CBMC 6.9.0, its bit-vector encoding, SAT/SMT machinery, and GOTO transformation are assumed sufficiently faithful and sound for the checked model.
2. **Source-model fidelity:** the compiled GOTO model is assumed to represent the selected preprocessed C build correctly.
3. **Integer widths:** `int16_t`, `int32_t`, and `int64_t` have the exact widths modelled by the toolchain.
4. **Signed right shift:** negative signed right shift is interpreted as arithmetic/sign-preserving in the recorded environment. This is not a universal ISO C portability proof.
5. **Frozen build configuration:** the recorded compile defines, include paths, and ML-KEM-768 configuration correctly expose the examined function.
6. **Source identity:** the frozen commit, tree, and `poly.c` hash identify the intended implementation.
7. **Oracle adequacy:** the independently written Euclidean oracle correctly formalizes the intended centered residue.
8. **Assertion adequacy:** the named properties capture the intended claims without missing a crucial condition.
9. **No binary refinement claim:** source/GOTO correctness is not automatically a proof that every optimizing compiler emits equivalent machine code.
10. **No hardware model:** processor faults, transient execution, undefined hardware behavior, and physical leakage are outside scope.

### 13.2 Property-specific scope restrictions

- P5 directly quantifies over alternative `int16_t` representatives, not unbounded integers.
- P8 constrains congruent pairs through a logical implication.
- T4 covers only nonnegative multipliers in `0..64513`, with offset and shift fixed.
- T5 covers offsets in `0..2^26-1`, with multiplier and shift fixed.
- T4 and T5 do not jointly synthesize multiplier, offset, and shift.
- The campaign does not prove that the constants are globally optimal according to every possible performance, area, leakage, or compiler criterion.

### 13.3 Security properties not proved

The campaign does not establish:

- constant-time behavior of generated machine code;
- cache, branch, power, EM, or timing leakage resistance;
- masking security;
- fault-injection resistance;
- compiler correctness;
- memory zeroization;
- correctness of unrelated ML-KEM functions;
- end-to-end ML-KEM encapsulation/decapsulation correctness;
- IND-CCA security;
- conformance of an entire library build to FIPS 203.

Those are different claims requiring different specifications and tools.

## 14. Did the campaign really prove `mlk_barrett_reduce` correct?

### 14.1 Answer within the declared scope

**Yes.** The campaign proved a precise source-level functional statement:

> For every `int16_t` input, the real body of `mlk_barrett_reduce` at frozen commit `af4c5abd...` returns exactly the independent centered representative modulo 3329, under the signed-arithmetic-right-shift semantics represented by the recorded CBMC environment.

T1.P4 is sufficient for this conclusion. T1.P2 and P3 are then explicit supporting properties; T1.P5 strengthens the characterization. T2 confirms canonicalization laws. T3–T5 explain the exact quotient structure and the relevant fixed-parameter design spaces.

### 14.2 Why this is stronger than testing

A passing test suite demonstrates correctness only for executed examples. The T1 harness gives `a` an unrestricted symbolic `int16_t` value, and CBMC checks the assertion for every bit pattern in that type. The target has no unbounded loop, so there is no incomplete loop-unwinding caveat for the core function. The full finite input domain is represented.

### 14.3 Why this is not universal truth about all executions everywhere

The proof is conditional on the model and trusted base. In particular, the C source acknowledges that signed right shift is implementation-defined for negative values. A platform using a different shift behavior would not be covered by this theorem. Likewise, machine-code compilation and side-channel behavior were not verified.

The accurate wording is **“proved correct within the recorded formal model and stated scope”**, not “proved absolutely correct under all conceivable environments.”

## 16. Novelty review

### 16.1 What “novel” can and cannot mean

No finite literature search can prove that an equivalent result has never existed in an unpublished note, private repository, non-indexed thesis, or inaccessible source. Therefore this report does not make a “1000% novel” or unconditional world-first claim.

Novelty is assessed at three levels:

1. **Mathematical novelty:** whether a new general theorem in modular arithmetic or constant division was discovered.
2. **Implementation-specific theorem novelty:** whether this exact property has been publicly reported for the frozen `mlkem-native` C function and domain.
3. **Method/evidence novelty:** whether the combined CBMC, control, mutation, source-binding, and forensic workflow is a distinct research contribution.

The campaign is strongest at levels 2 and 3. It is deliberately conservative at level 1.

## 17. Threats to validity

### 17.1 Specification validity

The independent oracle is concise and conventional, but a human still selected the intended centered interval and threshold. A mistaken specification could be proved faithfully. Mitigation: compare it with source documentation, FIPS-level modulus facts, boundary controls, and alternate properties.

### 17.2 Tool/model validity

CBMC and the GOTO transformation are part of the trusted computing base. Mitigation: preserve model dumps, property inventories, tool versions, and exact commands; use simple finite arithmetic obligations; add independent deterministic cross-checks.

### 17.3 Build validity

Preprocessor definitions and exposure of a file-local function could accidentally change semantics. Mitigation: retain source paths in model dumps, compare source hashes, avoid editing production source, and bind production output directly in P4, P10, P15, and P24.

### 17.4 Vacuity risk

Implications can pass when antecedents are unreachable. Mitigation: no input assumptions, concrete controls for antecedents/boundaries, symbolic full domains, and mutants that target exact bounds and witnesses.

### 17.5 Mutation representativeness

Twelve mutants do not exhaust all possible faults. They demonstrate targeted sensitivity, not complete fault-detection capability. T2 lacks dedicated mutants.

### 17.6 External validity

The results are tied to one frozen source commit, build configuration, and recorded shift semantics. A later commit or different platform requires revalidation.

### 17.7 Novelty-search completeness

The public search cannot cover unpublished, private, unindexed, non-English, or inaccessible work. The originality statement must remain qualified.

## 19. Professor-facing questions and precise answers

### “Did you modify the C function to make CBMC pass?”

No. The frozen production worktree remained clean. Mutated C copies were isolated outside that worktree and were used only as negative controls.

### “Did CBMC prove only the contract?”

The native repository harness primarily checks the contract. The BR-AF4 principal harnesses retain the real body and add explicit semantic assertions, including exact equality to an independent oracle and production bindings in T1, T3, T4, and T5.

### “Did assumptions force the result?”

No input-path assumptions were used in the principal harnesses. Restricted parameter sets were expressed with implications. There are still explicit modelling assumptions, especially signed right shift and CBMC/source-model fidelity.

### “Is this just exhaustive testing?”

No. Independent Python enumeration was used only as a cross-check/discovery aid. The authoritative result is a symbolic, bit-precise CBMC proof over the complete finite domains.

### “Why are T4 and T5 meaningful if general division-by-constant theory exists?”

General theory explains how reciprocal-multiplication bounds can be derived. T4 and T5 instantiate and machine-check exact parameter-space claims for a specific signed centered-reduction formula, domain, C implementation, and tool semantics, including source binding and mutation evidence.

### “Is 2^25 the only correct offset?”

No. T5 proves exactly the opposite: 11,666 offsets are full-domain correct in the declared design domain. `2^25` lies within the interval with margins 5,833 below and 5,832 above.

### “Is 20159 universally unique?”

No. It is unique only in T4’s declared nonnegative numerator-safe multiplier domain with modulus, offset, shift, intermediate model, and input domain fixed.

### “Did this prove all of ML-KEM?”

No. It proves a detailed theorem suite for one low-level modular-reduction function. Whole-algorithm correctness and cryptographic security are separate claims.
