# 3. Mathematical statement checked

For each coefficient index `i`, let:

```text
a = A[i]
b = B[i]
d = a - b
q = 3329
```

Under the precondition that `d` is representable as a signed 16-bit C value, the implementation sequence is expected to produce:

```text
R[i] ∈ [0, q)
```

and:

```text
R[i] ≡ d (mod q)
```

The concrete independent oracle used in the central semantic harness was equivalent to:

```c
(uint32_t)(d + 10 * 3329) % 3329
```

The use of `10 * 3329` ensures a non-negative dividend throughout the signed-16-bit difference domain used by the proof. OR-SR1 separately established that this expression equals the conventional canonical mathematical expression:

```c
((d % 3329) + 3329) % 3329
```

for every signed 16-bit `d`.

Therefore, the semantic equality checked by VC-SR1 was not accepted merely because it appeared plausible in the harness. The oracle itself received an independent proof obligation.

# 6. Production-callsite analysis

The relevant frozen decryption sequence in `mlkem/src/indcpa.c` was:

```c
mlk_unpack_ciphertext(b, v, c);
...
mlk_poly_invntt_tomont(sb);
mlk_poly_sub(v, sb);
mlk_poly_reduce(v);
mlk_poly_tomsg(m, v);
```

The important coefficient bounds were:

```text
0 ≤ v[i] < 3329
|sb[i]| < 26632
```

The inverse-NTT absolute bound was exclusive:

```text
MLK_INVNTT_BOUND = 8 * MLKEM_Q = 26632
```

Therefore:

```text
-26631 ≤ v[i] - sb[i] ≤ 29959
```

This interval is contained in:

```text
-32768 ≤ int16_t ≤ 32767
```

Thus, the subtraction used at the frozen production decryption callsite is signed-16-bit representable.

This result is essential. Without it, the central T1/VC-SR1 assumption would remain only a user-selected input restriction. AC-SR1 connects that restriction to the actual frozen decryption context.


## 8.2 Independent mathematical oracle

## 8.3 Explicit canonical-domain result

The campaign includes an implementation mutant and an assertion mutant. The native proof harness alone does not constitute these campaign-level falsification controls.

## 8.8 Separate evidence identity

The campaign harnesses live outside the frozen repository proof tree and have their own source paths, models, commands, results, hashes, and manifests.

Therefore, the campaign is not a duplicate of the repository-native `poly_sub` proof. It is a separate, scoped, composition-level semantic verification campaign built against the frozen production implementation.

Only the Barrett-reduction loop bound in `mlk_poly_reduce_c` was changed from:

The accepted positive harness, oracle, assumptions, solver checks, and frozen repository remained unchanged.

## 17.2 Why this mutation mattered

The mutation represented a realistic locality defect: one array element was skipped while the rest of the loop executed normally.

A weak, unreachable, tautological, or over-assumed semantic harness might allow such a mutant to survive.

CBMC rejected the mutant.


No. It is complete only for the frozen finite CBMC model and the recorded assumptions and configuration.

# 31. Why a new upstream-revision check was necessary

The original evidence was correctly bound to commit:

```text
d9613cf60de3132d32475c102d8c2781d84feb34
```

During the later repository audit, the remote `main` reference had advanced to:

```text
af4c5abdd5958bdc65a03cd5ee86708264f93304
```

The frozen local repository was therefore no longer byte-identical to the moving remote branch. This did not invalidate the original proof. It meant only that the proof remained a theorem about its frozen source revision and could not automatically be described as a proof of the newer upstream revision.

A broad first audit compared the frozen local commit directly with the newly fetched moving remote branch and consequently reported hundreds of differences and a final failure classification. That output was not evidence of repository corruption. It was evidence that two different revisions had been compared. The corrected audit instead asked the proper questions:

1. Does the frozen worktree exactly match its own recorded commit?
2. Is its Git object graph healthy?
3. Is the newer upstream revision a descendant of the frozen commit?
4. Did the target implementation or direct contract change?
5. Did supporting headers or proof build machinery change?
6. Can the unchanged proof artefact be rebuilt and solved against the newer source?

The frozen worktree passed its commit-pinned audit:

```text
HEAD=d9613cf60de3132d32475c102d8c2781d84feb34
TRACKED_TREE_COUNT=1124
INDEX_COUNT=1124
MISSING_TRACKED_FILES=0
LOCAL_TRACKED_CHANGES=0
GIT_CONNECTIVITY_CHECK=PASS
```

The newer target was then handled in a separate detached worktree. The original evidence tree was never reset, pulled, or overwritten.

## 31.1 What could have gone wrong if this check had not been performed

Without this revision check, the thesis could have made one or more materially incorrect statements:

- that a proof created for `d9613cf...` automatically proved the moving `main` branch;
- that the repository was corrupt because a moving-branch comparison produced differences;
- that no upstream changes had occurred;
- that proof artefacts and source code were bound when they were actually from different revisions;
- that a successful old CBMC result remained authoritative for a later build without replay;
- that a source-level theorem was portable even though shared macros, headers, compiler preprocessing, or build flags had changed;
- that the latest GitHub repository had been checked when only an older frozen snapshot had been checked.

Any of these statements would create an examiner-visible reproducibility defect. A professor could reasonably ask for the exact commit, the relation between that commit and upstream, the files that changed, and whether the proof was rerun. The version-drift analysis converted that potential weakness into a positive maintenance and portability experiment.

## 31.2 Thesis-writing consequences avoided by the check

The check prevented ambiguous phrases such as:

```text
The current mlkem-native implementation was proved correct.
```

The defensible wording is revision-specific:

```text

```

This distinction protects the thesis against overclaiming, stale evidence, and source/result mismatch.

# 35. Exact explicit properties in the semantic harness

The central harness contained 20 explicit assertion call sites. They fall into four groups.

## 35.1 Machine-model assertions: 8

The harness bound the intended platform semantics by asserting:

1. `CHAR_BIT == 8`;
2. `sizeof(short) * CHAR_BIT == 16`;
3. `sizeof(int) * CHAR_BIT == 32`;
4. `sizeof(int16_t) * CHAR_BIT == 16`;
5. `sizeof(int32_t) * CHAR_BIT == 32`;
6. `sizeof(void *) * CHAR_BIT == 64`;
7. arithmetic right shift of `-1` behaves as required;

# 40. Did this campaign prove `mlk_barrett_reduce` to be “really true”?

The answer requires three separate levels.

## 40.1 What was definitely established

The positive GOTO model contained the real portable-C call chain:

```text
main
  -> mlk_vc_sr1_poly_sub
  -> mlk_vc_sr1_poly_reduce
  -> mlk_poly_reduce_c
  -> mlk_barrett_reduce
  -> mlk_scalar_signed_to_unsigned_q
```

The Barrett helper body was present, reachable, and not replaced by a function contract. Its loop ID was present:

```text
mlk_barrett_reduce.0
```

and was included in the unwind plan with bound `2`.

For every symbolic polynomial coefficient satisfying the harness assumption, the complete real reduction chain produced the expected unsigned-canonical representative of the subtraction modulo `3329`. Therefore, within this composition and domain, the behaviour of `mlk_barrett_reduce` contributed to a mathematically correct final result.

M4 strengthened this conclusion. It changed only the `mlk_poly_reduce_c` loop so coefficient `255` skipped Barrett reduction. The unchanged semantic oracle rejected that implementation mutant. This demonstrates that the proof was sensitive to the presence of the reduction operation at every coefficient.

## 40.2 What was not independently established

The campaign did **not** isolate `mlk_barrett_reduce(a)` and prove, as a standalone theorem over its entire documented input domain, both:

```text
result is in the centered representative interval
```

and:

```text
result ≡ a (mod 3329)
```

against a direct independent mathematical oracle.

The public source documentation describes `mlk_barrett_reduce` as returning a centered representative congruent to its input modulo `q`, while the visible source contract guarantees the centered range. The current campaign proves a stronger composition-level final canonical relation, but it does not replace a dedicated standalone Barrett-reduction theorem.

## 40.3 Strongest honest conclusion for Barrett reduction

> The real portable `mlk_barrett_reduce` body was executed as a reachable dependency of `mlk_poly_reduce` in the positive proof. The complete subtraction-and-reduction composition produced the correct canonical modular result for the scoped symbolic domain, and an implementation mutation that skipped one coefficient’s Barrett reduction was killed. This is substantive compositional evidence for the helper. It is not an independently packaged universal proof of the standalone `mlk_barrett_reduce` specification.

A future dedicated Barrett campaign should introduce a separate `BR-SR1` harness with a direct oracle, full documented input domain, range and congruence assertions, constant/configuration binding, and targeted mutants of the Barrett constants and rounding operations.

# 43. Why the result matters for the thesis methodology

The work demonstrates why a controlled verification pipeline is more than a wrapper around an LLM or a single CBMC command.

A candidate harness can succeed for the wrong reason. It may:

- use assumptions that exclude all meaningful calls;
- contain an incorrect oracle;
- fail to call the intended production function;
- link a replacement implementation;
- have contracts substitute for executable bodies;
- leave loops partially unwound;
- check a stale commit;
- ignore a changed preprocessing environment;
- produce a successful result for an unreachable assertion;
- survive obvious mutations;
- lose provenance between the source, model, and final report.

The campaign’s deterministic gates addressed these risks. The role of AI, where used in the wider thesis workflow, is candidate generation, analysis assistance, and documentation support. The authoritative result comes from frozen source identity, inspectable harnesses, deterministic build commands, model inventories, CBMC results, negative controls, and human-reviewed claim boundaries.

This is a strong answer to the challenge that a general coding assistant can “just generate a harness.” Generation alone does not establish:

- source binding;
- assumption validity;
- oracle validity;
- non-vacuity;
- loop completeness;
- body reachability;
- mutation sensitivity;
- revision portability;
- reproducible evidence integrity.
