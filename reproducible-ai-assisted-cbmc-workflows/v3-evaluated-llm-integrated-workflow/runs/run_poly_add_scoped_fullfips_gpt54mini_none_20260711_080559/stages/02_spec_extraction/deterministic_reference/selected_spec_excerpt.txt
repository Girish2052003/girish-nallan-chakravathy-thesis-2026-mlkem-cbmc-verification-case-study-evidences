46:                                            Abstract
47: A key-encapsulation mechanism (KEM) is a set of algorithms that, under certain conditions, can be
48: used by two parties to establish a shared secret key over a public channel. A shared secret key that
49: is securely established using a KEM can then be used with symmetric-key cryptographic algorithms
50: to perform basic tasks in secure communications, such as encryption and authentication. This
51: standard specifies a key-encapsulation mechanism called ML-KEM. The security of ML-KEM is
52: related to the computational difficulty of the Module Learning with Errors problem. At present,
53: ML-KEM is believed to be secure, even against adversaries who possess a quantum computer.
54: This standard specifies three parameter sets for ML-KEM. In order of increasing security strength
55: and decreasing performance, these are ML-KEM-512, ML-KEM-768, and ML-KEM-1024.

76:    203).
77: 2. Category of Standard. Computer Security. Subcategory. Cryptography.
78: 3. Explanation. A cryptographic key (or simply “key”) is represented in a computer as a string of
79:    bits. A shared secret key is a cryptographic key that is computed jointly by two parties (e.g.,
80:    Alice and Bob) using a set of algorithms. Under certain conditions, these algorithms ensure
81:    that both parties will produce the same key and that this key is secret from adversaries. Such
82:    a shared secret key can then be used with symmetric-key cryptographic algorithms (specified
83:    in other NIST standards) to perform tasks such as encryption and authentication of digital
84:    information.
85:    This standard specifies a set of algorithms for establishing a shared secret key. While there
86:    are many methods for establishing a shared secret key, the particular method described in
87:    this standard is a key-encapsulation mechanism (KEM).
88:    In a KEM, the computation of the shared secret key begins with Alice generating a decapsu-
89:    lation key and an encapsulation key. Alice keeps the decapsulation key private and makes
90:    the encapsulation key available to Bob. Bob then uses Alice’s encapsulation key to generate
91:    one copy of a shared secret key along with an associated ciphertext. Bob then sends the
92:    ciphertext to Alice. Finally, Alice uses the ciphertext from Bob along with Alice’s private
93:    decapsulation key to compute another copy of the shared secret key.
94:    The security of the particular KEM specified in this standard is related to the computational
95:    difficulty of solving certain systems of noisy linear equations, specifically the Module Learn-
96:    ing With Errors (MLWE) problem. At present, it is believed that this particular method of
97:    establishing a shared secret key is secure, even against adversaries who possess a quantum
98:    computer. In the future, additional KEMs may be specified and approved in FIPS publications
99:    or in NIST Special Publications.

329: 1.     Introduction
330: 1.1 Purpose and Scope
331: This standard specifies the Module-Lattice-Based Key-Encapsulation Mechanism (ML-KEM). A
332: key-encapsulation mechanism (KEM) is a set of algorithms that can be used to establish a shared
333: secret key between two parties communicating over a public channel. A KEM is a particular type
334: of key establishment scheme. Other NIST-approved key establishment schemes are specified
335: in NIST Special Publication (SP) 800-56A, Recommendation for Pair-Wise Key-Establishment
336: Schemes Using Discrete Logarithm-Based Cryptography [2], and SP 800-56B, Recommendation
337: for Pair-Wise Key Establishment Schemes Using Integer Factorization Cryptography [3].
338: The key establishment schemes specified in SP 800-56A and SP 800-56B are vulnerable to
339: attacks that use sufficiently-capable quantum computers. ML-KEM is an approved alternative
340: that is presently believed to be secure, even against adversaries in possession of a large-scale
341: fault-tolerant quantum computer. ML-KEM is derived from the round-three version of the
342: CRYSTALS-KYBER KEM [4], a submission in the NIST Post-Quantum Cryptography Standardization
343: project. For the differences between ML-KEM and CRYSTALS-KYBER, see Appendix C.
344: This standard specifies the algorithms and parameter sets of the ML-KEM scheme. It aims
345: to provide sufficient information to implement ML-KEM in a manner that can pass validation
346: (see https://csrc.nist.gov/projects/cryptographic- module- validation- program). For
347: general definitions and properties of KEMs, including requirements for the secure use of KEMs
348: in applications, see SP 800-227 [1].
349: This standard specifies three parameter sets for ML-KEM that offer different trade-offs in security
350: strength versus performance. All three parameter sets of ML-KEM are approved to protect
351: sensitive, non-classified communication systems of the U.S. Federal Government.
352: 
353: 1.2 Context
354: Over the past several years, there has been steady progress toward building quantum computers.
355: If large-scale quantum computers are realized, the security of many commonly used public-key
356: cryptosystems will be at risk. This would include key-establishment schemes and digital signature
357: schemes whose security depends on the difficulty of solving the integer factorization and discrete
358: logarithm problems (both over finite fields and elliptic curves). As a result, in 2016, NIST initiated
359: a public Post-Quantum Cryptography (PQC) Standardization process to select quantum-resistant
360: public-key cryptographic algorithms. A total of 82 candidate algorithms were submitted to NIST
361: for consideration.
362: After three rounds of evaluation and analysis, NIST selected the first four algorithms for stan-
363: dardization. These algorithms are intended to protect sensitive U.S. Government information
364: well into the foreseeable future, including after the advent of cryptographically-relevant quan-
365: tum computers. This standard specifies a variant of the selected algorithm CRYSTALS-KYBER, a
366: lattice-based key-encapsulation mechanism (KEM) designed by Peter Schwabe, Roberto Avanzi,
367: Joppe Bos, Léo Ducas, Eike Kiltz, Tancrède Lepoint, Vadim Lyubashevsky, John Schanck, Gregor
368: Seiler, Damien Stehlé, and Jintai Ding [4]. Throughout this standard, the KEM specified here will
369: be referred to as ML-KEM, as it is based on the Module Learning With Errors assumption.

401:                           covered.

403:                           accepts the encapsulation key as input, requires private randomness,
404:                           and produces a shared secret key and an associated ciphertext as out-

407:                           during the encapsulation process. The encapsulation key can be made
408:                           public. (See Section 3.3.)
409:      encryption key       A cryptographic key that is used with a PKE in order to encrypt plaintexts
410:                           into ciphertexts. The encryption key can be made public.
411:      equivalent process   Two processes are equivalent if the same output is produced when the
412:                           same values are input to each process (either as input parameters, as
413:                           values made available during the process, or both).

583: 2.4 Interpreting the Pseudocode
584: This section outlines the conventions of the pseudocode used to describe the algorithms in
585: this standard. All algorithms are understood to have access to two global integer constants:
586: 𝑛 = 256 and 𝑞 = 3329. There are also five global integer variables: 𝑘, 𝜂1 , 𝜂2 , 𝑑𝑢 , and 𝑑𝑣 . All
587: other variables are local. The five global variables are set to particular values when a parameter
588: set is selected (see Section 8).
589: When algorithms in this specification invoke other algorithms as subroutines, all arguments (i.e.,
590: inputs) are passed by value. In other words, a copy of the inputs is created, and the subroutine
591: is invoked with the copy. There is no “passing by reference.”
592: Pseudocode assignments are performed using the symbol “←.” For example, the statement
593: 𝑧 ← 𝑦 means that the variable 𝑧 is assigned the value of variable 𝑦. Pseudocode comparisons
594:                                                  6
595: 
596: 
597: FIPS 203                                       MODULE-LATTICE-BASED KEY-ENCAPSULATION MECHANISM
598: 
599: 
600: are performed via the symbol “==.” For example, the expression 𝑥 == 𝑤 is a boolean value
601: that is TRUE if and only if the variables 𝑥 and 𝑤 have the same value.
602: In regular text (i.e., outside of the pseudocode), a different convention is applied. There, the
603: “=” symbol is used both for assigning values and for comparisons, in keeping with standard
604: mathematical notation. When emphasis is needed, assignments will be made with “∶=” instead.
605: Variables will always have a valid value that is appropriate to their data type, with two exceptions:
606:    1. The outputs of a random bit generator (RBG) have the byte array data type but are also
607:       allowed to have the special value NULL. This value indicates that randomness generation
608:       failed. This can only occur in ML-KEM.KeyGen and ML-KEM.Encaps.
609:    2. The outputs of ML-KEM.KeyGen and ML-KEM.Encaps have the byte array data type but
610:       are also allowed to have the special value ⊥. When ML-KEM.KeyGen or ML-KEM.Encaps
611:       return the value ⊥, this indicates that the algorithm failed due to a failure of randomness
612:       generation.

907: This section gives a high-level overview of the ML-KEM scheme.
908: 
909: 3.1 Key-Encapsulation Mechanisms
910: The following is a high-level overview of key-encapsulation mechanisms (KEMs). For details, see
911: SP 800-227 [1].
912: A KEM is a cryptographic scheme that, under certain conditions, can be used to establish a shared
913: secret key between two communicating parties. This shared secret key can then be used for
914: symmetric-key cryptography.
915: A KEM consists of three algorithms and a collection of parameter sets. The three algorithms are:
916:      1. A probabilistic key generation algorithm denoted by KeyGen
917:      2. A probabilistic ”encapsulation” algorithm denoted by Encaps
918:      3. A deterministic ”decapsulation” algorithm denoted by Decaps
919: The collection of parameter sets is used to select a trade-off between security and efficiency.
920: Each parameter set in the collection is a list of specific (typically numerical) values, one for each
921: parameter required by the three algorithms.

963: 3.2 The ML-KEM Scheme
964: ML-KEM is a key-encapsulation mechanism based on CRYSTALS-KYBER [4], a scheme that was
965: initially described in [8]. The following is a brief and informal description of the computational
966: assumption underlying ML-KEM and how the ML-KEM scheme is constructed.
967: 
968: The computational assumption. The security of ML-KEM is based on the presumed hardness
969: of the so-called Module Learning with Errors (MLWE) problem [9], which is a generalization of
970: the Learning With Errors (LWE) problem introduced by Regev in 2005 [10]. The hardness of the
971: MLWE problem is itself based on the presumed hardness of certain computational problems in
972: module lattices [9]. This motivates the name of the scheme ML-KEM.
973: In the LWE problem, the input is a set of random “noisy” linear equations in some secret
974: variables 𝑥 ∈ ℤ𝑛𝑞 , and the task is to recover 𝑥. The noise in the equations is such that standard
975: algorithms (e.g., Gaussian elimination) are intractable. The LWE problem naturally lends itself to
976: cryptographic applications. For example, if 𝑥 is interpreted as a secret key, then one can encrypt
977: a one-bit plaintext value by sampling either an approximately correct linear equation (if the
978: plaintext is zero) or a far-from-correct linear equation (if the plaintext is one). Plausibly, only a
979: party in possession of 𝑥 can distinguish these two cases. Encryption can then be delegated to
980: another party by publishing a large collection of noisy linear equations, which can be combined
981: appropriately by the encrypting party. The result is an asymmetric encryption scheme.
982: The MLWE problem is similar to the LWE problem. An important difference is that, in MLWE, ℤ𝑛𝑞
983: is replaced by a certain module 𝑅𝑞𝑘 , which is constructed by taking the 𝑘-fold Cartesian product
984: of a certain polynomial ring 𝑅𝑞 . In particular, the secret in the MLWE problem is an element 𝐱 of
985: the module 𝑅𝑞𝑘 . The ring 𝑅𝑞 is discussed in detail in Section 4.3.
986: 
987: The ML-KEM construction. At a high level, the construction of the scheme ML-KEM proceeds in
988: two steps. First, the ideas discussed previously are used to construct a public-key encryption (PKE)
989: scheme from the MLWE problem. Second, this PKE scheme is converted into a key-encapsulation
990: mechanism using the so-called Fujisaki-Okamoto (FO) transform [11, 12]. Due to certain prop-
991: erties of the FO transform, the resulting KEM provides security in a significantly more general
992: attack model than the PKE scheme. As a result, ML-KEM is believed to satisfy so-called IND-CCA2
993: security [1, 4, 13, 14].

1483: 4.3 The Number-Theoretic Transform
1484: The Number-Theoretic Transform (NTT) can be viewed as a specialized, exact version of the
1485: discrete Fourier transform. In the case of ML-KEM, the NTT is used to improve the efficiency of
1486: multiplication in the ring 𝑅𝑞 . Recall that 𝑅𝑞 is the ring ℤ𝑞 [𝑋]/(𝑋 𝑛 + 1) of polynomials of the
1487: form 𝑓 = 𝑓0 + 𝑓1 𝑋 + ⋯ + 𝑓255 𝑋 255 (where 𝑓𝑗 ∈ ℤ𝑞 for all 𝑗), with the ring operations defined
1488: by arithmetic modulo 𝑋 𝑛 + 1.
1489: The ring 𝑅𝑞 is isomorphic to another ring 𝑇𝑞 , which is a direct sum of 128 quadratic extensions
1490: of ℤ𝑞 . The NTT is a computationally efficient isomorphism between these two rings. When a
1491: polynomial 𝑓 ∈ 𝑅𝑞 is input, the NTT outputs an element 𝑓 ̂ ∶= NTT(𝑓) of the ring 𝑇𝑞 , where 𝑓 is

1688: 5.      The K-PKE Component Scheme
1689: This section describes the component scheme K-PKE. As discussed in Section 3.3, K-PKE is not
1690: approved for use in a stand-alone fashion. It serves only as a collection of subroutines for use in
1691: the algorithms of the approved scheme ML-KEM, as described in Section 7.
1692: K-PKE consists of three algorithms:
1693:      1. Key generation (K-PKE.KeyGen)
1694:      2. Encryption (K-PKE.Encrypt)
1695:      3. Decryption (K-PKE.Decrypt)
1696: When K-PKE is instantiated as part of ML-KEM, K-PKE inherits the parameter set selected for
1697: ML-KEM. Each parameter set specifies numerical values for each parameter. While 𝑛 is always
1698: 256 and 𝑞 is always 3329, the values of the remaining parameters 𝑘, 𝜂1 , 𝜂2 , 𝑑𝑢 , and 𝑑𝑣 vary
1699: among the three parameter sets. Parameters and parameter sets are described in Section 8.
1700: The algorithms in this section do not perform any input checking because they are only invoked as
1701: subroutines of the main ML-KEM algorithms. The algorithms of ML-KEM themselves do perform
1702: input checking as needed.
1703: Each of the algorithms of K-PKE is accompanied by a brief, informal description in text. For
1704: simplicity, this description is written in terms of vectors and matrices whose entries are elements
1705: of 𝑅𝑞 . In the actual algorithm, most of the computations occur in the NTT domain in order to
1706: improve the efficiency of multiplication. The relevant vectors and matrices will then have entries
1707: in 𝑇𝑞 . Linear-algebraic arithmetic with such vectors and matrices (e.g., line 18 of K-PKE.KeyGen)
1708: is performed as described in Sections 2.4.7 and 4.3.1. The encryption and decryption keys of
1709: K-PKE are also stored in the NTT form.
